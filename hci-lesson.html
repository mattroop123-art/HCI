Topic 1 of 3

Evaluation questions

A usability test begins with a question about people performing a task, rather than a general request for opinions. An evaluation question states what you need to learn about an interface. It connects a design uncertainty to an observable behavior so the session can produce useful evidence.

For a registration portal, “Do students like the website?” is broad and may produce preferences without revealing task problems. A more focused question is: “Can a first-time user locate an open class that fits their schedule and add it without assistance?” This identifies the user group, task, and outcome while leaving room to observe how the user proceeds.

Separate the research question from the instruction shown to participants. The team may want to know whether a filter is discoverable, but telling someone to “use the availability filter” reveals the intended solution. Instead, ask them to find a class that meets a realistic need and observe whether they discover the control themselves.

A focused question does not automatically explain why a user struggles. Combine task outcomes with observations, comments, and the sequence of actions. If someone fails to register, the cause might be unclear navigation, misleading labels, a system error, or an unrealistic task—not necessarily the feature you initially suspected.

Topic 2 of 3

Task selection

Test tasks should represent what users actually need to accomplish and should address the design uncertainties you identified. A task scenario gives a goal and enough context to act, while avoiding instructions that disclose the exact controls to use.

For example: “You need a three-credit course that meets after noon and does not conflict with your existing schedule. Find a suitable open section and add it.” This allows different valid paths while giving the participant a clear objective. “Click Search, open Advanced Filters, and select Afternoon” tests compliance with instructions rather than whether the interface communicates a usable path.

Select a manageable mix of important, frequent, and potentially difficult tasks. Include recovery when it matters, such as removing an accidentally added class or resolving a schedule conflict. Use realistic data and prepare the starting state so participants are not blocked by missing accounts or unrelated setup problems.

Task order also matters. An earlier task may teach navigation needed for a later one. When comparing designs or testing discoverability, consider varying task order or separating novice tasks so learning effects do not masquerade as design improvements. Pilot the scenarios to catch unclear wording before recruiting the full group.

Topic 3 of 3

Success thresholds

Before testing, define what counts as success and what evidence will be recorded. A success criterion makes task completion observable; a threshold specifies the level of performance the design should achieve. These decisions should follow user needs and the consequences of failure, rather than being chosen after seeing results.

For registration, successful completion might mean that a valid, nonconflicting section appears in the schedule and the participant recognizes that it was added. You might distinguish independent success, success with assistance, partial completion, and failure. Clicking Add without reaching the correct final state is insufficient.

Record more than one measure when needed. Task success answers whether the goal was reached; time on task measures effort over a defined interval; errors reveal wrong actions or recoveries. State when timing begins and ends, what assistance means, and which mistakes count as errors so observers use the same rules.

A small exploratory test can reveal important issues without giving a precise population estimate. If four of five participants succeed, report the observed result and the problems encountered; do not treat it as proof that exactly 80% of all users will succeed. Agree on practical acceptance goals in advance, then interpret the evidence with the sample size and study design in mind.
